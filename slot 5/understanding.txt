Use perf stat on the server process — you already know how from Slot 1. Count context switches, page faults, cache misses. Use cat /proc/interrupts before and after to see which IRQs hit your core.

Block A — The packet receive path. (~3–4 hours)
This is the chain you already have. The goal is to be able to draw it on a whiteboard with each transition labeled. Topic sequence:
NIC hardware (PHY/MAC layer, what arrives) → DMA engine and ring buffer (what is a ring buffer, who allocates it, who owns the descriptors) → hardware interrupt + IRQ routing (which core, MSI-X vectors) → NAPI and softirq (why polling replaced pure interrupts, NET_RX_SOFTIRQ, ksoftirqd) → sk_buff allocation (what an sk_buff is, why it's expensive) → protocol processing (IP, UDP, checksumming) → socket receive queue (per-socket buffer, SO_RCVBUF) → recv() syscall and the kernel→user copy.


The single best source for this, by a wide margin: Joe Damato's "Monitoring and Tuning the Linux Networking Stack: Receiving Data" on the packagecloud blog. It walks the path with kernel source line numbers. Read it once for shape, then once with notes. Skip the parts about tunable sysctls on first pass — you want the path, not the knobs.

Supplementary, only if Damato leaves you confused on a specific step: LWN's "A JIT for packets" (for the XDP / pre-stack hook context) and Cloudflare's "Why we use the Linux kernel's TCP stack" (good for the philosophy of why this thing is shaped the way it is).

Deliverable: a single-page diagram in your notes — boxes for each step, arrows labeled with the data structure that crosses, a column on the right with the typical latency contribution of each step (µs or ns).

Block B — The noise sources on an isolated core. (~2–3 hours)
This is your Q2 Part A gap from the original diagnostic interview, where you got two out of five. The right list, in roughly decreasing order of how often it bites HFT:
Timer tick interrupt (the 1000Hz / 250Hz scheduling clock) → SMI (System Management Interrupt, firmware-level, invisible to OS) → IRQ delivery to your core (other devices' interrupts routed to your CPU) → page faults (minor and major) → TLB shootdowns (cross-core IPI to invalidate TLB entries) → C-state transitions (CPU going to sleep between bursts) → cache pollution from neighboring hyperthread.

For each, you need three things: mechanism (one sentence), detection command (one command), fix (one or two sentences). That's the interview answer shape.

Sources: there is no single canonical text for this — it's accumulated tribal knowledge. The best consolidation I've seen is Erik Rigtorp's blog ("Low Latency Tuning Guide" — read the whole thing, it's short and brutal). For SMIs specifically: the Red Hat "Realtime Tuning Guide" and the turbostat tool docs. For the timer tick and nohz_full: Frederic Weisbecker's LWN articles. For TLB shootdowns: there's an excellent Cloudflare blog post titled "How to receive a million packets per second" that touches it indirectly, but the cleanest treatment is the kernel documentation on mm/tlb.c plus a quick read of what MADV_DONTNEED triggers.
Deliverable: a markdown table with seven rows (the seven noise sources), four columns (mechanism, detection command, fix, typical magnitude in µs). Keep it on one screen. This is the table you reference in interviews.

Block C — What kernel bypass actually does. (~1–2 hours, only after A and B are solid)
This is small but load-bearing. Once Block A is internalized, kernel bypass is a one-page idea: the NIC DMAs into userspace-mapped memory, the application polls the ring buffer directly, the entire bottom half of the kernel stack (interrupt → softirq → sk_buff → protocol stack → socket queue → copy) is removed. Your recv() becomes a memory read.
What it removes: everything from "hardware interrupt" down to "kernel→user copy" in Block A. What it does not remove: everything in Block B. That's the entire Part B answer from the original diagnostic.
Source: read the OpenOnload Implementation white paper (the 2008 USENIX one by Steven Pope and David Riddoch) for the historical-canonical version. Then skim the current Xilinx/Solarflare OpenOnload user guide for the production reality. Do not read these before A and B — you'll memorize jargon without intuition.
Deliverable: one paragraph, written in interview-answer structure (essence-mechanism-point), titled "What kernel bypass removes and what it doesn't." This is the answer to the Part B question you couldn't answer cold.

Block D — Diagnostic instrument map. (~1 hour, last)
This is a lookup table, not a study topic. One column: the layer (NIC, ring buffer, softirq, sk_buff, socket queue, application). Second column: the instrument that reads that layer's counter (ethtool -S, /proc/interrupts, /proc/net/softnet_stat, slabtop, ss -unmp, your own HdrHistogram). Third column: what a healthy reading looks like.

You only build this after A and B are in place, because otherwise the column names will be vocabulary, not anchors. Source: man pages plus your own UDP echo experiments — run each command against your running server and note what changes when you generate load.
Deliverable: the table itself, in your repo as diagnostic_instruments.md.
