C2. What does OpenOnload actually do? Not "bypasses the kernel" — specifically, what mechanism does it use? (Answer: it provides a userspace shared library that intercepts socket syscalls and redirects them through a userspace TCP/UDP stack. Under the hood it uses ef_vi to DMA packets directly into userspace-mapped memory. Your application calls recv() normally — Onload's LD_PRELOAD intercept catches it and reads from the userspace ring buffer instead of entering the kernel.)


1. Application Injection (LD_PRELOAD)OpenOnload forces the operating system to load OpenOnload’s custom userspace shared library into your application’s memory space before the standard C library (glibc)

2. Syscall Interception Because the Onload library is loaded first,
it hooks, intercepts and replace networking system calls with own network stack 
so when recv() called it never do context switch into kernel instead library caches function and serve is directly from userspace.

3. Direct Memory Mapping (The Hardware Bridge) 
Solarflare NIC driver allocates memory for packet buffers and maps that memory space directly into your application's virtual address space

For the intercepted calls to actually read data, the hardware must be able to talk to userspace. During initialization, the Solarflare NIC driver allocates memory for packet buffers and maps that memory space directly into your application's virtual address space.

4. DMA via ef_vi Under the hood, Onload relies on ef_vi, Solarflare’s lowest-level Virtual Interface API. The NIC is programmed to use Direct Memory Access (DMA) to push incoming network packets directly across the PCIe bus and into the userspace ring buffers created in Step 3. The kernel's network stack, interrupt handlers, and packet copying mechanisms are completely cut out of the data path.

5. Userspace Protocol Processing When your intercepted recv() call executes, Onload's custom TCP/UDP stack simply polls that userspace ring buffer. It handles all the complex protocol logic — TCP state machines, acknowledgments, reassembly, and checksums — right there in the application thread. It then hands the payload back to your application just as a standard recv() would.

6. The Kernel FallbackOpenOnload is a hybrid stack. If your application makes a socket call that isn't destined for the accelerated Solarflare interface (like an SSH connection, or routing to a management subnet), the Onload library acts as a passthrough. It hands the syscall back to the standard Linux kernel to be processed normally, ensuring you don't lose standard OS networking capabilities.

C4. Where does ef_vi sit relative to OpenOnload? Where does TCPDirect sit? (Answer: ef_vi is the raw Layer 2 API — direct NIC access, no protocol stack, you build everything yourself. OpenOnload sits on top of ef_vi and gives you a full TCP/UDP stack with BSD socket compatibility. TCPDirect sits between them — lower latency than Onload, simpler than ef_vi, but requires API changes in your application.)


The Kernel Bypass Stack Hierarchy
1. ef_vi (The Foundation)

Position: The absolute bottom of the user-space stack, interfacing directly with the NIC's DMA engine and queues.

What it is: The raw Layer 2 API.

The Trade-off: It provides the absolute lowest latency and highest message rate physically possible on the hardware. However, it offers zero protocol support. There is no IP routing, no TCP state machine, and no UDP header parsing. You are simply passing raw Ethernet frames back and forth, meaning you have to build the entire protocol stack yourself.

2. TCPDirect (The Middle Ground)

Position: Sits immediately above ef_vi, acting as a custom transport layer.

What it is: A highly optimized, user-space TCP and UDP stack.

The Trade-off: TCPDirect strips away the overhead of trying to emulate standard operating system behaviors. It gives you lower latency and better predictability than OpenOnload, but it sacrifices compatibility. You cannot just drop it into an existing system; it requires proprietary API changes, meaning your application code must be explicitly rewritten to talk to TCPDirect.

3. OpenOnload (The Application Wrapper)

Position: Sits at the top of the user-space stack, bridging the gap between high-performance hardware (like ef_vi) and standard software interfaces.

What it is: A full user-space TCP/IP stack coupled with complete POSIX / BSD socket compatibility.

The Trade-off: It is designed for zero-code-change deployment. Your application can still execute standard recv(), send(), and epoll() calls, and OpenOnload intercepts them (usually via LD_PRELOAD) to bypass the kernel. It sacrifices a small amount of latency to maintain this standard interface, making it slightly slower than TCPDirect, but massively easier to deploy.
